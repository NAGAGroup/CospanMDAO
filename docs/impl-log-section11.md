Beyond the spec: a child that is gone and is not made transient is rebuilt at once (so an override from pre_forward can revive a transient that was deleted); a transient is rebuilt at the next precompute. ## P5: shapes and hooks

Commits 1cad7ab (code and converted tests) and the tests/log commit after it. Decisions:

- **set_shape(out, e0, e1, ...).** One entry per dimension, an integer or `cs::as_is`; an entry count that differs from the rank throws. `VarMeta::set_by_producer` refuses every number first (`refuse_number`), then sets; nothing changes when a check throws. A number on a specified dimension throws at the call, even when it matches ("dimension N is declared as V; set_shape('x') takes a number only on an unspecified dimension (pass cs::as_is)"); on a hook-owned one: "dimension N is owned by a shape hook; ... cannot give it a number". Ragged keeps the RaggedShape copy form and (n, counts); n may be `cs::as_is`; `(n, cs::as_is)` sets n alone. The old full-range form, `check_same_forward`, `dim_text`, `dim_equal`, `set_forward_` and `set_log_` are removed (no "two sets in one forward must agree").
- **Ownership rules.** `SetterId::Kind` gained `definition` (fixed dimensions are applied by the definition). `check_setter`: a producer or initializer setting a fixed dimension fails ("a specified dimension comes from the definition"); the hook rules are unchanged.
- **Tied members.** `Instance::tied_member`, set by `tie_outputs` and by the replay of a tie on a rebuilt member. `settable_output` throws the existing tied message when `tied_member` or the variable's `tied_output` is set (the second covers a member reached through a promotion).
- **Hook targets.** A hook may target an untied output; it runs before the first child holding it (the producer, which passes `as_is` for hooked dimensions). A tied member output is refused at the call: "... hook the tie alias instead ('t')".
- **Templated step.** One `detail::ShapeHookStep<D...>` per shape_hook call (descriptor types as template parameters, compile-time dispatch), stored in the System as a `HookEntry` behind `detail::HookBase` (only `forward(Runtime&)`). Behavior kept: from_value reads batched into one wait; counts_from / offsets_from use the device scan and bring back only the total.
- **Run point.** `compute_hook_slots` and the source-ordering check are removed. `place_hooks()` finds each hook's slot (the first child holding the target) at the start of the System's compute; the loop runs the hook when it reaches it. A gone source keeps the last shape; a shape never known throws the shape-not-known error. Tests that expected the setup error now check that setup succeeds.
- **Anywhere.** `shape_hook` and `depends_on` lost the setup-only guard. add_subsystem and the marks keep it.
- **declare_init / init_input** on an already-materialized free input marks it stale, like update_input (`System::init_input` passes restale; replay does not).

## P7a: fused groups, part 1

Commits 761df85 (single launch path through indexed call sequences) and d749f1b (segments, range modes, local memory, the new fuse_components API, tests/test_fused_groups.cpp), plus the log commit after them. Authority: docs/plan-section11.md P7, design review 11.6. Decisions:

- **One launch path.** Every plain-body and group-body component (bare or in a group) launches through `detail::GroupLauncher` (include/naga/cospan/group_launch.hpp). A bare component is a group of one stage (`solo_` member of ComponentBase). Custom-op and host components keep their own `submit` path. The old per-component static JIT config, `launch_individual`, `launch_wave`, `StageRecord`, `jit_config<KB>` and the four packing buffers with their staging code are deleted.
- **Stage function.** `detail::stage_fn<KB>` is a SYCL_EXTERNAL function template with the one signature `(StageItem<R>, const StageGeometry*, const void* const*, int stage)`. It reads `geometry[k]` and `args[k]`, builds the GroupItem (or the plain id) and calls the body. Its dynamic_function_definition id is a function-local static in `stage_definition_id<KB>()`, reached through the virtual `ComponentBase::definition_id()`. Users see only GroupItem.
- **Kernel.** One generic kernel per body kind and rank calls the noinline placeholder `run_stages_r1/r2/r3(item, geometry*, args**, int)`, defined with `define_as_indexed_call_sequence(&run_stages_rN, {stage ids}, 3)`. Index parameter 3 is the int stage index; the fork replaces it with the constant k per definition (also for a single definition). `launch_group` passes 0 as the placeholder.
- **Config cache (decision and reason).** `detail::group_config(rank, defs)` returns a `dynamic_function_config` from a process-wide cache that is never destroyed (`static Cache* = new Cache`, mutex plus map), keyed by (rank, vector of definition symbol names); an id handle is the function name pointer. Reason (P1c finding): a config must outlive every kernel that uses it, and a transient group can be deleted before the JIT has run, so a config owned by a group (or by a static with destructor order) is not safe. Test: a transient group rebuilt every forward.
- **Argument container.** Per component, a 1-element `usm_vector<StageArgs<KB>>` on its device (`reserve(1)`, so the address is final). Each forward `compute` fills the host member `KernelLaunch<KB>::args_` and the launcher copies it in (`stage_upload`, a container write); the launch reads it.
- **Pointer array.** Allocated, filled and waited on at the group first precompute (`GroupLauncher::prepare`); redone only when the group is rebuilt.
- **Geometry array.** Group-owned, one `StageGeometry` per stage (group_count, group_base, segment_groups, ticket_state (null), segment, segments, stages, local_offset, local_bytes, range_mode), filled every forward from a host member and copied with event ordering. After the n entries it holds a table of uint64 segment block sizes, rounded up to whole entries; the stage function finds it at `geometry + stages`.
- **Segments and range.** A segment is a run of consecutive stages that share groups; its block is the largest group count of its stages; the launch is the sum of the blocks. The stage function skips when group_count == 0, group < group_base, or the segment group is past the block; in `own` mode also when the segment group is past the stage own count. A plain body masks `flat >= flat_extent`. In `whole` mode the GroupItem group range widens dimension 0 to the block (`delinearize_open`). GroupItem: `get_group_*` relative to the segment from 0, `get_segment()`, `get_segment_count()`, `get_segment_group_count(s)`.
- **Work-group check.** Every forward, before launch: all stages must have the same local range, else `invalid_argument` naming the stages ("... different work-group shapes ...").
- **Local memory.** `KernelParts::local_bytes` = Scratch plus bytes requested through `LaunchDescription::request_local_bytes(n)` (each request rounded to 16). `partitioned` (default): a segment size is the sum and each stage offset the running sum; `shared`: offset 0 and the size is the max. The launch local block is the largest segment size; over the device limit throws ("bytes of local memory", naming the stages). `GroupItem::local<T>(n)` is a typed bump allocator starting after the Scratch, nullptr when the slice is exhausted.
- **API (spelling).** `cs::fuse_components("name", cs::connects_desc({...}), items...)` and `cs::fuse_components("name", items...)`; an item is a bare component descriptor (a one-stage segment) or `cs::segment<opts...>(descs...)`. Options: `cs::local_mem::partitioned|shared`, `cs::range_mode::own|whole` (at most one of each kind; static_asserts). `system_from` is unchanged. The result type is `FusedGroup<Items...>` (was `FusedComponent<S, ...>`). The compile-time rules are kept (no custom-op or host stages, all plain or all group, one rank).
- **Removed.** `fuse_strategy::seq|par`, `FusedComponent<S, ...>`, `fuse_components<S>`, the packing buffers. The par-connect rejection is gone: a connect inside a group is allowed in either range mode (the forward-order check is P7b), so the test "fused parallel: a connect between stages throws" was deleted and the value-driven par section now expects setup to succeed.
- **Ports.** Old seq = one segment holding all stages with `range_mode::whole`; old par = each stage its own segment. tests/support.hpp has `cst::fuse<cst::FuseMode::seq|par>` for the existing tests (a test helper, not API). examples/gemver-chain/systems.hpp uses the segment spelling directly; the barrier variant still compiles (P8 removes it).
- **Pool numbers.** The per-component argument array, and a group launcher pointer array and geometry array, are pool containers like any other, so the pool-in-use expectations in test_model, test_system and test_flavors gained `cst::solo_launch_bytes(k)` (three nodes per kernel component). `cst::group_launch_bytes(stages)` exists in support.hpp but is not used yet. This follows the spec reading that they are containers on the component device.
- **Kept.** The "no ragged ports in a fused group" setup check.
- **Tests (tests/test_fused_groups.cpp, [fused_groups]).** Two segments with each stage seeing its own count; a bare descriptor as a one-stage segment; own vs whole (group range seen); shared local memory (stage 2 reads stage 1 values after a barrier); partitioned local memory (disjoint slices); work-group shape mismatch error; a bare component; one component type in two groups; a transient group rebuilt every forward.
- **Open.** The forward-order check for connects inside a group is P7b. README and the gemver README still describe `fuse_components<seq|par>` in places; diagnostics.hpp comments still say "packing-buffer uploads"; not rewritten.

## P7b: fused groups, part 2 (boundaries, ticket mode, waits, connect order)

Commit 6118a48 (code and tests) and the log commit after it. Decisions:

- **Boundary items.** (Since changed: see the last entry; `global_barrier` is now the only one.) The first version had a ticket-order item as well as `cs::global_barrier()`; both returned `detail::BoundaryItem<Boundary::...>`; they are items of `fuse_components`, between two segments. The boundary stands before the NEXT segment (`SegmentSpec::boundary`). Placement (not first, not last, not next to another boundary) and "stages are all group-body" are `static_assert`s of `FusedGroup` (compile time, so no setup error exists); the conditions are the traits `detail::boundaries_placed_ok<Items...>()`, `detail::has_boundary_v<Items...>` and `stage_checks<...>::all_group`, which the tests check (a wrong group does not compile, so it has no runtime test).
- **Boundaries only in group-body groups (decision to log).** A plain-body group is refused boundaries: a plain body has no work-group to cooperate with (no group barrier, no leader, no collective wait), and the collectives would have no meaning for it.
- **Ticket mode.** Any boundary in a group puts the whole launch in ticket mode; a group without one keeps the hardware group id and allocates nothing (geometry `ticket_state` stays null: one load in the kernel). In the generic kernel (`launch_group`, before the stage sequence) the leader does `fetch_add` (relaxed) on the ticket counter and broadcasts it (`sycl::group_broadcast`). The ticket replaces the hardware linear group id as `StageItem::group` (new field), which the stage function uses for its skip logic; the ticket maps to (segment, group within segment) through the geometry's segment block sizes, so GroupItem indices come from the ticket with no other change.
- **Ticket state.** A `usm_vector<uint32_t>` owned by the launcher: word 0 the ticket counter, words 1..S the per-segment completed counters, then one flag per ticket (1 + S + total groups words). Each forward: resized if the size changed and filled with 0 (container fill ordered after the previous launch, passed explicitly as `prior = read_deps()` because an outside writer is not in the fill's own wait lists); the launch waits on `read_deps()` (the fill) and registers itself with `register_write`. The pointer is in every geometry entry. The segment table of the geometry array is now the S block sizes followed by the S boundary kinds (none / the removed ticket-order kind / global_barrier).
- **Completion recording.** After the stage sequence, in ticket mode: group barrier, `atomic_fence(release, device)`, then the leader stores the group flag and `fetch_add`s the segment counter, both `release`. It is recorded in the kernel (after every stage of the group ran; the stages of other segments skipped this ticket), so a stage with `own` range that skips does not matter.
- **global_barrier.** Before the stage sequence, a group of a segment whose boundary is `global_barrier` has its leader spin (acquire loads) until every earlier segment's counter equals its block, then a group barrier and an acquire fence. The removed ticket-order item added no wait.
- **GroupItem waits.** `wait_group(s, g)` (spins on the flag of ticket `blocks[0] + .. + blocks[s-1] + g`) and `wait_earlier_segments()` (spins on the counters of segments before the current one). Both are `const`, collective (leader spins, group barrier, acquire fence), no checks and no branches: with a null ticket state the behavior is undefined, and waiting on your own or a later segment never returns. No debug assert was added.
- **No co-residency needed.** A group only ever waits for groups with earlier tickets, and every earlier ticket is held by a group that has started, so the wait cannot deadlock however many groups the launch has. The cases with `big_shape()` use 4 x the compute units groups of the largest work-group the device allows (up to 1024).
- **Connect order.** `FusedGroup::setup` checks each connect before making it: stage index = the first path component looked up among the stages in item order; if source index >= target index it throws through `wiring_fail`: "naga::cospan: System 'f': connect: 'b.x' reads 'a.y', which runs after it in fused group 'f'" (the group path). Forward connects are allowed in every range mode. A path that names no stage is left to `connect` to report.
- **Tests (tests/test_fused_groups.cpp, [fused_groups][tickets], [errors]).** the ticket-order item kept segment/group indices; global_barrier neighbor-group read; ticket-order + `wait_group` on the neighbor group; `wait_earlier_segments` giving the same result; each of the three in a small shape (5 groups of 64) and the big shape, over 5 forwards with a new input each forward (a stale ticket state or a missed wait shows); boundary placement and plain-group traits; backward, same-stage and cross-segment backward connects. The chained prefix with look-back was NOT built (kept simple, as the task allowed): the wait_group case is a neighbor-group read.
- **Open.** README / gemver README still describe `fuse_components<seq|par>`; diagnostics.hpp comments still say "packing-buffer uploads". The cuda big case relies on max_work_group_size (1024 on this GPU); whether it exceeds co-residency depends on the GPU (not measured).
- Suites: default 237 cases (227 passed, 10 skipped, 2302 assertions); cuda three runs, each `All tests passed (2363 assertions in 237 test cases)`.

## Resize events: shape-hook column resizes feed the target's slot

## Fused groups: group_waits_enabled replaces the ticket-order boundary

- **Design correction (Jack).** The ticket-order boundary item (the former `cs::` function) was never intended; the first implementation (6118a48) added it by reading the design review's "ticket ordering" bullet as an item. Group waits are a PROPERTY of the fused group, and `cs::global_barrier()` is the only boundary item. It is removed outright, with no deprecated stub; no public name or user-facing doc says "ticket" any more (internal identifiers and comments keep it).
- **Spelling.** `cs::fuse_components<cs::group_waits_enabled>(name, [connects_desc(...),] items...)`: a tag type given as a template option, in the style of `cs::segment<cs::local_mem::shared, ...>`. A plain `fuse_components(...)` with no options still works (both overloads are `template <class... Opts, class... Items>`). `FusedGroup<bool Waits, Items...>` carries the flag.
- **What it does.** With the property, stages may use `GroupItem::wait_group(s, g)` and `wait_earlier_segments()` on earlier segments' work-groups. The group's flag (`FusedBase::group_waits_`) is `Waits || has_boundary_v<Items...>` and is passed to `GroupLauncher::launch(..., group_waits)`; it replaces "any boundary" as what switches the counter, reset and completion recording on. Those are unchanged. `Boundary` is now `{none, global_barrier}`. A group with neither property nor barrier uses hardware ids and allocates no wait state, as before.
- **static_asserts** (fused_component.hpp): `FusedGroup`: "naga::cospan: cs::group_waits_enabled is for groups of work-group stages: a plain-body group has no work-group to wait with"; "naga::cospan: cs::global_barrier() is for groups of work-group stages: a plain-body group has no work-group to cooperate with"; "naga::cospan: a cs::global_barrier() goes between two segments: not first, not last, and not next to another barrier". `fuse_components` (both overloads): "naga::cospan: the only fuse_components option is cs::group_waits_enabled".
- **Small addition for the tests.** `GroupLauncher::has_wait_state()` and `FusedBase::has_wait_state()` (true once a forward of a group with group waits has allocated the ticket state), so a test can check that a group with neither property nor barrier allocates none.
- **Tests (tests/test_fused_groups.cpp, tag renamed [tickets] -> [group_waits]).** `neighbor_case<Mode, Kind>` is parameterised by property (Kind 1: `fuse_components<cs::group_waits_enabled>` with no barrier) vs barrier (Kind 2). Renamed: "group_waits_enabled gives the launch its wait state and the segments keep their values" (also checks `has_wait_state()`), "group_waits_enabled with wait_group on a neighbor group of the earlier segment". Added: "wait_group works in a group that has only a global_barrier" (`neighbor_case<1, 2>`), "a group with neither group_waits_enabled nor a global_barrier allocates no wait state", and the plain-stage rejection as trait checks (`Checks<PlainDesc, PlainDesc>::all_group` false, `is_fuse_option_v`) next to the existing boundary checks. `tests/support.hpp` unchanged (cst::fuse needs no option).
- **Docs.** design-review section 11 "Boundary primitives", spec r03 (6.2-6.6, departures 4, 6, 14, 16), README, ROADMAP, gemver README. docs/plan-section11.md is left as it was (historical): it still names the removed item, so a grep for the old function name is not empty there. Older entries of this log say "ticket-order item" for the removed item.
- Suites: default 240 cases (230 passed, 10 skipped, 2386 assertions); cuda `All tests passed (2447 assertions in 240 test cases)`.

## Initializers: an implicit zero on undeclared inputs; reshape re-initializes free inputs

- **The bug.** `Var::first_materialization` only initialized when `init` was set, so a free input with no initializer was never initialized; since SlabKit `4f57086` allocations are uninitialized, such an input held garbage. Commit ca0e6fe had worked around it in the tests (explicit `fill(0)` / `zero()` updates, size-only checks) instead of fixing it.
- **Rules (agreed with Jack).** (a) An input declared without an initializer gets an implicit zero initializer and is stale until it runs. (b) The implicit zero is not a declaration: a cycle still needs an explicit one (the first-materialization error still fires); in a tie any explicit initializer beats an implicit one in either order, the last explicit one wins; no merge site lets an empty initializer replace an explicit one. (c) A connected input never initializes (except a cycle with an explicit initializer); outputs never do. (d) A reshape of a materialized variable with no producer (free input, `tie_inputs` alias) marks it stale, so its initializer (explicit or implicit zero) runs again on the new shape; re-initializing valid data is accepted.
- **Code.** variable.hpp: `first_materialization` initializes when `(!output_asked || cycle) && (init || !has_producer())` (the existing else-branch of `initialize` is the zero fill, `fill(T{})`); `apply_shape` sets `stale_` when `!has_producer()`, so `materialize` re-runs `reinitialize`; comments fixed. `VarMeta::init` stays the DECLARED initializer (empty = none declared), which is what keeps every merge site correct: `fold_init`, `merge_connected`, `apply_tie_merge`, `System::replay_connect` and `declare_init` all copy only a set initializer (wiring.hpp comments say so; no logic change was needed there).
- **Tests restored** (what they checked before ca0e6fe): test_component InitDemo `d` zero by default (title and comments too); the custom-op recorder test keeps only its pointer checks (outputs never initialize); test_system "init_input on an eternal free input" (y = 1 first), the tie_inputs `from_output_shape` case (x zeros at each new size), the placement rebuild (`filled(0.0f)`); test_p4 merge-error case and the replay case (`filled(1.0f)`); test_model update_input on a connected input.
- **Tests added.** test_p4: a cycle with no explicit initializer still throws. test_system: reshape re-runs the implicit zero (free input with a hook, sizes 3/6/4/8) and a declared fill(7); reshape of a tie_inputs alias re-runs both kinds; a tie with one explicit fill and one implicit gets the fill, with either member declaring it; a tie with two explicit initializers takes the last; a connected input and an output keep what the producer wrote while the chain is reshaped. All check final values through the Model; no library counters or accessors were added.
- **Spec.** r03 section 3.4 replaces "undefined values" with these rules.
- Suites: default 247 cases (237 passed, 10 skipped, 2435 assertions); cuda `All tests passed (2496 assertions in 247 test cases)`.

## Fused groups: ties declared in fuse_components (cs::ties_desc)

- **API.** `cs::fuse_components[<options>](name, [cs::connects_desc(...)], [cs::ties_desc(...)], items...)`; connects first when both are given, and every existing call (including `cs::fuse_components<cs::group_waits_enabled>(...)` and `cst::fuse`) compiles unchanged. `cs::ties_desc({cs::tie_outputs<DT, R>({"a.y", "b.y"}, "y" [, shape [, policy]]), cs::tie_inputs<DT, R>({...}, "x" [, shape])})`: each entry takes the parameters of `System::tie_outputs` / `System::tie_inputs` with the same defaults, minus the device (the group's own). The entries are `cs::TieEntry` (a `std::function<void(detail::FusedBase&)>`) in a `cs::TiesDesc`; `FusedGroup` now takes `(ConnectsDesc, TiesDesc, items...)` and the four `fuse_components` overloads are told apart by `requires` on `leads_with_connects_v` / `leads_with_ties_v`.
- **Reuse, no duplicated validation.** The bodies of the public `System::tie_inputs` / `tie_outputs` moved into protected `tie_inputs_of` / `tie_outputs_of` over a `std::span<const std::string_view>` (the public calls forward to them; `resolve_members` and `record_tie` take the span too). The group's entries call them through `FusedBase::group_tie_inputs` / `group_tie_outputs`. The alias lives in the group (`f.<name>`), is recorded for replay like any System tie, and every tie rule applies (policy, no ties of ties across levels, tied members cannot set_shape, hooks by path, push suppression).
- **Order in setup.** Stages, then ties, then connects (a tie refuses members that are already connected; a connect may name an alias).
- **Push.** `FusedBase::run_compute`: `check_tied_output_devices()` (the run-time member-device check kept), the single launch, then `push_own_tied_outputs()` (new protected System helper: the same `push_tied_output` the loop uses, for every alias the System owns). The copies wait on the alias container's write list, which holds the launch's write; their events join `FusedBase::events()`. No ordering or pattern checks among tied stages.
- **Tests (tests/test_fused_groups.cpp, [ties]).** Atomic outputs of three stages (a zeroing stage, then two adders, since outputs are never initialized) and plain outputs under allow_plain (each stage writes its own slice), checking the views of `f.a.y`, `f.b.y` and `f.y`; connects_desc plus ties_desc together; a shape hook on `f.y`; an input tie read by two stages through `f.x`; a consumer outside the group reading `f.y` in the same forward; an owner-level tie with paths into the group; errors: a tie of a tie in both directions across levels (the owner ties a group-tied member: "already tied"; the owner ties the group's alias: "tying a tie is not allowed"), set_shape on a tied member, a plain dtype under require_atomic, a member path that does not exist. A connect from the alias to a stage that must run after the writers has to share their plain segment (stages of one plain segment run per index in stage order; separate segments are unordered), which is the designer's responsibility.
- Suites: default 255 cases (245 passed, 10 skipped, 2476 assertions); cuda `All tests passed (2537 assertions in 255 test cases)`.


## Launch redesign: rank-3 physical launches, cs::range_split strategies, CoSpan item and group wrappers

- **Why.** Groups were flattened in four places: `group_nd_range` laid every group along SYCL dimension 0 (capped at 65535 groups for rank 2 and 3 on CUDA, so a rank-2 launch of 65,793 groups died with `could not submit kernel from module (CU:1)`), `stage_upload` returned one linear count, `pad3` put the rank dimensions first, and plain bodies always launched as a flat range. All four are gone.
- **Physical launch.** Every launch is `sycl::nd_range<3>`; a stage's range and work-group shape are in the trailing dimensions with leading 1s (`pad3`, `default_wg` moved: `{1,1,128}`, `{1,8,8}`, `{4,4,4}`). One placeholder `run_stages(StageItem, ...)` replaces `run_stages_r1/r2/r3`; `stage_fn<KB>` is compiled against the rank-3 item, one definition per component type; `group_config(defs)` is keyed by the definitions alone. The one-rank and one-work-group-shape checks stay. A bare component is the native launch (one segment, `Split::pad`).
- **stage_upload** returns the stage's per-dimension group range (`sycl::range<3>`, all 0 for an empty stage): ceil(range / wg) for plain and group bodies alike. A plain body gets a rank-R index masked per dimension against its range; `flat_extent`, `delinearize*`, `first_dims` and the flat-index path are removed.
- **Strategies.** `cs::range_split::flatten_and_split` (default), `pad_and_split`, `padded`: a `fuse_components<...>` option next to `cs::group_waits_enabled`, at most one (`static_assert`); `FusedGroup<bool Waits, detail::Split Sp, Items...>`. A segment's block is the per-dimension maximum of its stages' group ranges; `own` skips groups outside the stage's own range in any dimension, `whole` shows the stage the block. `padded` with a rank-3 stage is a `static_assert` (`detail::split_supports_rank_v`, also the trait the test checks).
- **Segment table.** `detail::SegmentInfo` per segment: range[3], count, first ticket, offset along the last dimension, boundary. `StageGeometry` lost `group_count`, `group_base`, `segment_groups` and gained `total_groups`, `split`.
- **Tickets.** Ticket -> (segment, rank-R group) is segment-major then row-major, last dimension fastest, for every strategy (`locate_linear`); the ticket state is `1 + S + total logical groups`; a physical group drawing a ticket at or past the total returns before any completion write. The wait atomics and fences are unchanged; `global_barrier` and `wait_earlier_segments` compare with the per-segment product. Without tickets, `locate_physical` maps the hardware id (flatten: linear along dimension 2; pad: by the segment's offset; padded: dimension 0).
- **Wrappers.** `GroupItem<R>` wraps `nd_item<3>` with `to_sycl()` and an implicit conversion; `get_group()` returns the new `cs::Group<R>` (stage-rank group id and range, `to_sycl()` to `sycl::group<3>`, implicit conversion, `leader()`); `wait_group(s, sycl::id<R>)`; `get_segment_group_count(s)` returns `sycl::range<R>`. The SYCL 2020 group functions are free functions in `cs::` over `cs::Group<R>` (the list is in the spelling table); `cs::sub_group` aliases `sycl::sub_group`. SYCL's argument orders are kept: `exclusive_scan_over_group(g, x, init, op)` but `inclusive_scan_over_group(g, x, op, init)` (the first draft had them the same and failed to compile on `std::plus` as an init).
- **Ported.** `examples/gemver-chain/components.hpp`, `tests/test_component.cpp`, `tests/test_flavors.cpp`, `tests/test_fused_groups.cpp` (`cs::group_barrier`, `cs::reduce_over_group`, `wait_group(0, sycl::id<1>{..})`, `get_segment_group_count(..)[0]`). `tests/spike` and `device_scan.hpp` are untouched (raw SYCL kernels outside CoSpan).
- **Tests (tests/test_range_split.cpp, [range_split]).** Final values only. Per strategy: three segments of different shapes; own and whole (a flag grid zeroed in segment 0 behind a barrier, each stage adds 1 per group); tickets with `wait_group` on a rank-2 neighbour and with a global_barrier (4 forwards, 20 x 13 groups); 260 x 260 = 67,600 groups per stage in a fused group. Also: 67,600 groups in a bare rank-2 group component and a bare plain component; rank-3 stages (flatten, pad) with a bare rank-3 component; rank 1; the physical coordinates a stage sees through `to_sycl()` per strategy and for a bare component (the launch is the declared range); one case for every group-function family; `to_sycl()` into raw `sycl::reduce_over_group`; the traits. 30 new cases.
- Suites: default 285 cases (275 passed, 10 skipped, 2928 assertions); cuda `All tests passed (2989 assertions in 285 test cases)`.
